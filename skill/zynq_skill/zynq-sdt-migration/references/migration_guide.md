版本 1.0，2026-10-26。

本技能面向 Zynq-7000 裸机软件与 no-OS 驱动在 Vitis SDT 平台下的接口适配。它提供一套可交给开发者或 AI 助手执行的排查工作流，并附有经过实际开发验证的失败案例。

## 1. 目标与适用范围

在涉及 JESD204 等 IP 的系统开发中，IP 配置、硬件构建工具和 PS 软件平台可能存在版本依赖。将开发环境统一到 Vivado/Vitis 2025.2 时，除验证硬件兼容性外，还需核对 BSP 与 no-OS 适配层的接口语义。

本技能重点处理两类问题。

- 编译阶段因 BSP 头文件、设备宏和函数接口变化而失败。
- 编译通过，但 SPI、GPIO 或其他底层外设初始化失败，最终表现为外部芯片初始化异常。

适用条件如下。

| 项目 | 条件 |
|---|---|
| 处理器 | 首先面向 Zynq-7000 Cortex-A9 |
| 操作系统 | standalone 裸机环境 |
| 驱动结构 | 应用层、no-OS 通用层、Xilinx 平台适配层、AMD BSP 驱动 |
| 目标环境 | Vitis 2025.2，使用 SDT 方式生成的平台 |
| 典型外设 | PS SPI、PS GPIO、PS UART、计时与延时服务 |
| 必要前提 | 硬件交接信息与实际下载的比特流一致，板卡及外设连接明确 |

本技能可迁移到使用相同驱动结构的其他传感器、数据转换器和通信控制项目。迁移时需重新确认实际 SPI 实例、引脚、时钟和板级配置。

## 2. 准备输入

执行前收集以下内容，无需上传完整工具安装目录。

1. 处理器型号、工具版本和平台的构建方式。
2. 实际编译命令，尤其是 `SDT` 等预处理宏。
3. 当前 BSP 的 `xparameters.h`、SPI/GPIO 配置表及查找函数。
4. no-OS 通用层与平台适配层的初始化源码。
5. 应用入口中调用平台初始化和外部芯片初始化的代码。
6. 一次完整的编译错误或启动日志。
7. 如有，保留已验证可运行的 ELF、比特流和初始化配置，作为控制变量比较的基线。

所有路径、串口号和板级参数均由使用者提供。不要将示例中的地址或实例编号直接推广到其他硬件。

## 3. 快速执行流程

| 步骤 | 操作 | 应得到的结果 |
|---|---|---|
| 1 | 确认正在编译和下载的文件 | 源码、ELF、比特流、硬件交接信息及初始化脚本有明确对应关系 |
| 2 | 检查 BSP 条件编译分支 | 明确当前是否定义 `SDT`，以及实际生效的函数签名 |
| 3 | 追踪设备标识的完整传递过程 | 区分 no-OS 总线编号和 BSP 基地址 |
| 4 | 在平台适配层完成转换 | 保留通用层所需编号，向 BSP 传入当前接口所需参数 |
| 5 | 检查初始化返回值和对象初值 | 失败后停止后续芯片操作，并打印错误 |
| 6 | 核对计时、GPIO 和 SPI 配置 | 不依赖未经验证的兼容宏或固定频率假设 |
| 7 | 编译并完成一次板上启动 | 初始化返回成功，外设状态读取与预期一致 |
| 8 | 归档修改与验证范围 | 写清已证明的功能，以及尚未验证的算法和性能 |

优先处理可复现的第一个错误。下层尚未初始化成功时，不通过反复增加上层超时时间掩盖故障。

## 4. 核心规则与操作方法

### 4.1 区分每一层的参数含义

设备编号和设备基地址可能都是整数，编译器通常无法发现二者混用。

| 层次 | 本案例中的参数含义 | 应检查的源码 |
|---|---|---|
| 应用层 | 选用哪个 SPI 控制器 | 初始化参数及板级配置 |
| no-OS 通用层 | 用于查表的逻辑总线编号 | `no_os_spi_init()`、`spi_table` 和编号范围检查 |
| 平台适配层 | 将通用配置转换为 BSP 参数 | `spi_init_ps()` 等函数 |
| AMD BSP，非 SDT 分支 | 根据设备 ID 查找配置 | 当前 BSP 的 `XSpiPs_LookupConfig()` |
| AMD BSP，SDT 分支 | 根据基地址查找配置 | 当前 BSP 的 `XSpiPs_LookupConfig()` |

本案例的 no-OS 实现包含如下检查。

```c
if (param->device_id > SPI_MAX_BUS_NUMBER)
    return -EINVAL;
```

本案例中 `SPI_MAX_BUS_NUMBER` 为 8。将 PS SPI 基地址 `0xE0006000` 填入这个字段，会在调用 BSP 前返回 `-EINVAL`。因此，仅凭 BSP 查找接口变化，就全局替换所有名为 `device_id` 的字段，是不完整的适配方式。

这些结论适用于检查过的代码版本。其他 no-OS 版本可能具有不同的数据结构和约束，应先阅读实际实现。

### 4.2 在适配层转换，不破坏通用层语义

以下是单个 PS SPI 控制器的示例。实际应用应确认所选硬件实例。

在应用或板级配置中保留逻辑编号。

```c
/* no-OS bus index, not an MMIO base address. */
#define SPI_DEVICE_ID 0U
```

在平台适配层调用 BSP 前执行映射。以下代码展示接口适配方法，应结合实际文件和函数名集成。

```c
static XSpiPs_Config *lookup_ps_spi_config(uint32_t bus_id)
{
#ifdef SDT
    switch (bus_id) {
    case 0U:
        return XSpiPs_LookupConfig(XPAR_XSPIPS_0_BASEADDR);
    default:
        return NULL;
    }
#else
    return XSpiPs_LookupConfig((u16)bus_id);
#endif
}
```

在初始化函数中检查返回值。

```c
xdesc->config = lookup_ps_spi_config(param->device_id);
if (xdesc->config == NULL)
    goto ps_error;
```

若存在多个控制器，为每个逻辑编号分别配置映射。不能将所有编号都映射到同一基地址。

本案例实际 BSP 的 SDT 查找实现还允许参数 `0` 选择配置表中的首个实例。因此，不能声称把调用参数改为 `0` 就必然查找失败。本技能建议显式映射到具体基地址，以避免依赖首实例顺序；同时仍需修正后续控制器和时钟选择分支。

同时检查后面的控制器选择和时钟选择分支。如果其输入仍是 no-OS 总线编号，`switch (param->device_id)` 应匹配 `0`、`1` 等编号，而不是基地址。

本案例仅有一个 PS SPI 实例，编号 `0` 对应当前 BSP 中的 `XPAR_XSPIPS_0_BASEADDR`。不要据此推导其他硬件的控制器顺序。

### 4.3 核对时钟宏，保留分频计算

本案例在 Zynq 平台下使用如下条件映射，其他平台应重新核对生成的头文件。

```c
#if defined(PLATFORM_ZYNQ)
#ifdef SDT
#define SPI_CLK_FREQ_HZ(dev) (XPAR_SPI ## dev ## _SPI_CLK_FREQ_HZ)
#else
#define SPI_CLK_FREQ_HZ(dev) (XPAR_PS7_SPI_ ## dev ## _SPI_CLK_FREQ_HZ)
#endif
#endif
```

从当前 `xparameters.h` 获取 SPI 输入时钟，继续用已有分频逻辑计算目标 SPI 时钟。不要为了消除宏错误，任意填入一个能通过编译的频率。

### 4.4 初始化对象，并阻止错误继续传播

先清零应用初始化参数，避免未显式赋值的字段带入不确定值。

```c
struct no_os_spi_init_param spi_param = {0};
```

本案例中的 BSP 会在 `XSpiPs_CfgInitialize()` 开始时检查实例的 `IsBusy`。因此为实例分配清零内存。

```c
xdesc->instance = (XSpiPs *)no_os_calloc(1, sizeof(XSpiPs));
if (xdesc->instance == NULL)
    goto ps_error;
```

在应用入口检查平台初始化结果。

```c
int32_t platform_status = platform_init();
printf("platform_init status=%ld\r\n", (long)platform_status);

if (platform_status != 0) {
    printf("STOP: platform initialization failed\r\n");
    while (1) {
    }
}
```

该示例适用于调试阶段。产品实现可使用项目约定的错误处理和恢复机制。

平台初始化内部也应及时处理错误。串行执行初始化时优先保留首个失败位置，不要被后续赋值覆盖。SPI 传输失败时应将错误传给调用者，不能无条件报告成功。

### 4.5 分别检查 GPIO、UART 和计时服务

不要因 SPI 的设备标识存在两层含义，就对其他驱动机械地采用同一种改法。

| 接口 | 检查要点 |
|---|---|
| GPIO | 确认通用层是否使用编号查表，平台层的 `XGpioPs_LookupConfig()` 实际接收什么，以及当前引脚方向和输出使能是否正确 |
| UART | 确认日志和命令使用的 UART 实例、基地址、波特率及物理串口一致；本案例使用 UART0 |
| 计时 | 检查 `XTime` 声明、计时器实现、频率来源、初始化流程和实际计数是否递增 |
| 延时 | 检查单位换算和实际执行情况，避免只修复头文件而忽略运行行为 |

本案例的头文件适配方式如下。

```c
#ifdef SDT
#include "xiltimer.h"
#else
#include "xtime_l.h"
#endif
```

这是经过检查的 BSP 配置对应的用法，不代表所有 SDT 平台都具有相同计时实现。若使用自定义链接脚本，还应检查计时器初始化所需的启动段是否保留。

本案例中计时频率来自有效的 Cortex-A9 配置，最终关键修复是 SPI 标识的分层适配。因此，不把某个频率宏为零或一次 PLL 超时直接当成计时器故障的证据。

## 5. 失败案例与自我纠错过程

### 5.1 首先观察到的现象

应用能够编译、下载和运行，但启动时出现如下现象。

- 时钟器件初始化告警。
- 射频 PLL 校准等待超时。
- 本振设置流程继续执行，但读回频率为零。
- 后续采集等待超时。

这些信息出现在上层芯片初始化阶段，不能仅凭告警文字认定外接时钟缺失。

### 5.2 曾考虑但没有解决问题的方向

检查了超时单位换算和计时相关配置。调整超时换算后，启动故障仍存在，因此没有将该修改当成根因修复。

在硬件连接、比特流和 PS 初始化脚本保持一致的条件下，使用已验证的基线 ELF 能够完成外设初始化。这一次比较将排查重点收敛到当前 PS 软件和驱动适配，不需要反复逐个检查所有硬件 IP。

该比较只能缩小范围，不能单独证明硬件所有功能都正确。

### 5.3 确认的关键问题

为适配 SDT 接口，曾将 SPI 的应用配置字段设置为基地址。但该字段首先经过 no-OS 通用层的总线编号检查，因此底层 SPI 初始化未被调用。

应用入口没有检查平台初始化返回值，部分芯片访问封装也没有传播传输错误，导致程序继续运行，最终显示为芯片状态读取异常和 PLL 超时。

本地软件复现使用实际 no-OS 源码，以及模拟的底层初始化函数，得到以下结果。

```text
base-address ID: return=-22 driver_called=0 descriptor_null=1
bus-number ID:   return=0 driver_called=1 descriptor_null=0
```

这是软件控制流程验证，不是 SPI 电气通信测试。

### 5.4 修复与板上结果

保留 no-OS 逻辑总线编号，在平台适配层映射到 SDT 基地址，修正相关选择分支，并增加对象清零和平台返回值检查。重新编译、下载并从板卡重新上电的状态启动后，获得如下日志摘录。

```text
platform_init status=0
AD9528_initialize successful!
MCS successful
CLKPLL locked
AD9371 ARM version 5.1.1
PLLs locked
Calibrations completed successfully
FMC_AD9371 config successful!
tx_lo_freq=800000000Hz
rx_lo_freq=800000000Hz
RF System Initial Successful
```

以上是人工提供的实际板上日志的关键行摘录，不是由模板生成的预期结果。日志未包含的行已经省略。

多个相关修改一并完成后恢复正常，因此不把恢复效果分别归因于每一处辅助修改。SPI 标识错误具有源码证据和独立的软件复现依据，对象清零及返回值检查则用于消除不确定行为并改善错误定位。

## 6. 故障定位表

| 观察结果 | 优先检查 | 判断边界 |
|---|---|---|
| 找不到设备宏或头文件 | 当前 BSP 的宏定义、条件编译和实际包含路径 | 不依靠宏别名推测接口语义 |
| `no_os_spi_init()` 返回 `-EINVAL` | 参数指针、操作函数、总线编号范围 | 根据实际返回分支定位，不能将所有 `-EINVAL` 都归因于基地址 |
| no-OS 返回失败，BSP 初始化未被调用 | 通用层范围检查和配置字段 | 优先修复通用层输入 |
| `LookupConfig()` 返回空指针 | 参数类型、基地址和配置表 | 检查 SDT 实际分支 |
| 本振读回零或 PLL 超时 | 平台初始化、SPI 返回值、芯片访问，再检查时钟条件 | 单一告警不能排除软件故障 |
| 应用停在串口接收函数 | 是否正在等待新命令、CPU 是否运行 | 正常等待不等于死机 |
| 基线 ELF 正常，当前 ELF 异常 | 当前应用、BSP、编译选项和启动过程差异 | 只有控制变量一致时才有比较价值 |

## 8. 验证范围与失效条件

### 已完成的验证

- 在 Vivado/Vitis 2025.2、Zynq-7000 `xc7z100ffg900-2` 和 Cortex-A9 standalone 平台上完成实际启动。
- 在所检查的 no-OS 实现中复现基地址被误用为总线编号时的拒绝初始化行为。
- 完成 SPI 标识适配后，平台、时钟器件和射频器件初始化成功，并读回预期的 800 MHz 本振频率。
- 后续完成一次 TX 直接连接 RX 的 1024 点采集。去均值后的归一化复相关系数幅值约为 0.9986，作为系统基本收发已恢复的辅助证据。

上述结果不构成模型数值正确性、外接放大器补偿效果或全部性能指标通过的证明。

### 需要重新适配的情况

- Linux 驱动、设备树运行时访问、PYNQ Overlay 或其他非 standalone 软件结构。
- Zynq UltraScale+、Versal 或其他处理器平台。
- 不同 no-OS 版本改变了总线编号含义、初始化流程或结构体布局。
- 使用多个 SPI 控制器、PL SPI、不同片选方式或不同硬件引脚。
- BSP 的函数签名、设备配置宏或计时器实现与本案例不同。
- 硬件交接信息、比特流、PS 初始化脚本和 ELF 不匹配。
- 板级供电、连线、外设时钟或器件状态本身存在问题。

本技能没有证明 JESD204 IP 可以任意跨版本替换，也不替代 IP 授权、硬件约束、实现时序和板级检查。JESD204 仅是本案例的系统背景，PS 驱动的分层适配方法不依赖该协议。

## 9. 复用完成标准

对另一个项目执行本技能后，应交付以下最小结果。

1. 一份设备标识在各软件层中的含义和转换关系表。
2. 一份可定位到文件和函数的最小修改说明。
3. 一份首个错误已修复的实际编译或板上验证记录。
4. 一份仍未验证的功能和适配边界说明。

目前仅有一套实际硬件的验证依据。其他团队可复用其中的排查方法和适配模板，但仍须在自己的平台上完成验证。
